Part 1

Open Source & Licenses

What is Open Source?

Software whose source code is public, under a license that lets you:

  • Use it for any purpose
  • Study it and modify it
  • Redistribute copies
  • Share your modified versions

Linux, Python, Rust, Android, VS Code, Firefox... you already depend on it.

No license = NOT open source

Public code on GitHub without a license is all rights reserved by default.

  • People can read it, but legally can't reuse or modify it
  • The license is what grants permission
  • Always add a LICENSE file to a project you want shared

The Licenses You Should Know

LicenseTypeIn short
MITPermissiveDo almost anything, keep the copyright notice
Apache-2.0PermissiveLike MIT + explicit patent grant
GPL-3.0CopyleftDerivatives must stay GPL and open
AGPL-3.0Strong copyleftGPL, also applies to network/SaaS use

Not sure? MIT for simplicity, GPL if you want improvements to stay open. Use choosealicense.com.

Anatomy of a Healthy Repo

  • README.md: what it is, how to install and run it
  • LICENSE: what others may do with it
  • CONTRIBUTING.md: how to propose changes
  • SECURITY.md: how to report vulnerabilities privately
  • .gitignore: what must never be committed

Part 2

Git Fundamentals

Why Version Control?

Without it: project_final_v2_REAL_final.zip

  • Full history: who changed what, when, and why
  • Go back to any previous state
  • Experiment safely on branches
  • Work in parallel with a team

Git ≠ GitHub

Git

  • Tool on your machine
  • Distributed version control
  • Works fully offline
  • Created by Linus Torvalds (2005)

GitHub

  • Website hosting Git repos
  • Issues, PRs, Actions, Pages
  • Collaboration layer
  • Alternatives: GitLab, Codeberg

The Three Areas

Working Directory  --git add-->  Staging Area  --git commit-->  Repository
 (your files)                  (next snapshot)                   (history)
  • Working directory: files as you edit them
  • Staging area: what goes in the next commit
  • Repository: permanent history in .git/

Your First Repo hands-on

mkdir hello-git && cd hello-git
git init
echo "# Hello Git" > README.md
git status
git add README.md
git commit -m "Add README"
git log --oneline

The Daily Loop

git status            # what changed?
git diff              # see unstaged changes
git add file.txt      # stage a file (git add . for all)
git diff --staged     # see what will be committed
git commit -m "msg"   # save the snapshot
git log --oneline --graph

Good Commit Messages

  • One logical change per commit
  • Imperative, short subject: "Fix login redirect bug"
  • "stuff", "fix", "final2" help nobody
  • Explain the why in the body when it isn't obvious

.gitignore & Secrets

.env
node_modules/
__pycache__/
*.log
target/

Never commit passwords, API keys, tokens, or private keys.

Deleting the file later doesn't help: it stays in history. If a secret leaks, revoke and rotate it immediately.

Undoing Things

git restore file.txt            # discard unstaged edits
git restore --staged file.txt   # unstage, keep edits
git commit --amend              # fix the last commit (local only)
git revert <commit>            # new commit that undoes one (safe)
git reset --hard <commit>       # DANGEROUS: rewrites, loses work

Never rewrite history that others have already pulled.

Part 3

Branches, Merges & Conflicts

Branches

A branch is just a lightweight pointer to a commit.

git branch                 # list branches
git switch -c feature/login  # create + switch
# ... edit, add, commit ...
git switch main
git merge feature/login
git branch -d feature/login  # clean up

Rule of thumb: main stays working; every change happens on a branch.

Branch Types & Naming

TypePurposeExample
mainStable, always working codemain
FeatureNew functionalityfeature/login-page
BugfixFix a non-urgent bugfix/null-pointer-profile
HotfixUrgent fix for productionhotfix/leaked-api-key
ReleasePrepare and stabilize a versionrelease/1.2.0
Docs / ChoreDocumentation, tooling, cleanupdocs/update-readme
  • Branch from main, keep branches short-lived and merge back through a PR
  • Naming: type/short-description, lowercase, hyphens, no spaces
  • GitHub Flow (main + feature branches) suits most projects; Git Flow adds develop and release branches for versioned software

Merge Conflicts

Two branches changed the same lines. Git asks you to decide.

<<<<<<< HEAD
print("Hello from main")
=======
print("Hello from feature")
>>>>>>> feature/login
  1. Edit the file: keep what you want, delete the markers
  2. git add file
  3. git commit

Part 4

GitHub & the PR Workflow

Remotes: Connecting to GitHub

git remote add origin git@github.com:USER/hello-git.git
git push -u origin main     # first push
git push                    # later pushes
git pull                    # fetch + merge teammates' work
git clone <url>             # copy a remote repo locally

Issues

  • Track bugs, ideas, and tasks
  • Good bug report: expected vs actual, steps to reproduce, environment
  • Look for labels: good first issue, help wanted
  • Comment before starting so work isn't duplicated

The Fork & Pull Request Workflow

  1. Fork the repo to your account
  2. Clone your fork
  3. Branch: git switch -c fix/typo
  4. Commit your changes
  5. Push to your fork
  6. Open a PR against the original repo
  7. Iterate on review feedback (new commits on the same branch)

A Good Pull Request

  • Read CONTRIBUTING.md first
  • Small and focused: one problem per PR
  • Clear title and description, link the issue (Fixes #12)
  • Be polite and patient with reviewers; feedback is not personal

Other GitHub Tools

  • Actions: CI/CD (run tests on every push)
  • Pages: free static site hosting
  • Projects
